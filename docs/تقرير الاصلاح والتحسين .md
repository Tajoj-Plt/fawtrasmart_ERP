## 1. عروض الأسعار في المبيعات

**السؤال:** ما هي عروض الأسعار في المبيعات؟
**الإجابة:** هي تقديم عرض سعر لمجموعة من المنتجات.

**الإصلاحات المطلوبة:**
- تعديل الضريبة — لا تعمل حالياً.
- تعديل الوحدات — لا تعمل حالياً.
- قبل تحويل عرض السعر إلى فاتورة: مراجعة والتأكد من الخصم.
- التأكد من احتساب الخصم في الشجرة (شجرة الحسابات).
- التأكد من احتساب التحويل بين الوحدات.
- التأكد من أن الضريبة يتم اختيارها من المكان المناسب.
- التأكد من الشحن ورسومه.
- ضبط رسوم الشحن من الإعدادات.
- مراجعة قواعد الفاليديشن (Validation).

## 2. إدارة الفواتير الدورية

**السؤال:** ما هي إدارة الفواتير الدورية؟
**الإجابة:** هي الفواتير التي تصدر آلياً كل فترة زمنية.

**الإصلاحات المطلوبة:**
- التأكد من أن جدولتها مرتبطة بالـ Cron Job.
- التأكد من إرسال البريد الإلكتروني للعميل فور صدورها.
- التأكد من أن الخصم يُحسب بالطريقة الصحيحة.
- التأكد من تضمين الوحدات والتحويل بينها وتضمينها في الفاتورة.
- التأكد من الضريبة وأنه يتم احتسابها.
- إنشاء قالب بريد إلكتروني مخصص للفواتير الدورية.
- التأكد من أن عملية الدفع تتم بنجاح وأن النقود تُودَع في الخزينة.
- مراجعة قواعد الفاليديشن (Validation).
- حساب رسوم الشحن إن توفّر.

## 5. اتفاقية التقسيط (Installment Agreement)

**السؤال:** ما هي اتفاقية التقسيط؟
**الإجابة:** هي العقد أو الخطة التي تحدد كيفية سداد مبلغ معين على دفعات. بمعنى آخر، الاتفاقية هي **الخطة الرئيسية**.

**البيانات التي تحتويها:**

| # | الحقل | # | الحقل |
|---|---|---|---|
| 1 | العميل | 10 | نسبة الفائدة أو المرابحة (إن وجدت) |
| 2 | الفاتورة أو العقد المرتبط | 11 | نسبة الضريبة (إن وجدت) |
| 3 | المبلغ الإجمالي | 12 | رسوم إدارية |
| 4 | الدفعة المقدمة | 13 | غرامة التأخير |
| 5 | المبلغ الممول | 14 | حالة الاتفاقية (نشطة، مكتملة، متعثرة، ملغاة) |
| 6 | عدد الأقساط | 15 | العملة |
| 7 | قيمة القسط | 16 | الساعي (Tenant) |
| 8 | تاريخ أول قسط | | |
| 9 | دورية السداد (شهري، أسبوعي، كل 15 يوماً…) | | |

**مثال:**

| البند | القيمة |
|---|---|
| العميل | أحمد |
| قيمة الفاتورة | 120,000 |
| دفعة أولى | 20,000 |
| المبلغ الممول | 100,000 |
| عدد الأقساط | 10 |
| قيمة القسط | 10,000 |
| أول قسط | 2026-08 |

**الإصلاحات المطلوبة:**
- إصلاح الشريط الجانبي.

## 6. الأقساط (Installments)

**السؤال:** ما هي الأقساط؟
**الإجابة:** كل صف يمثّل قسطاً واحداً ناتجاً عن الاتفاقية.

**مثال:**

| رقم | تاريخ الاستحقاق | المبلغ | الحالة |
|---|---|---|---|
| 1 | 1 أغسطس | 10,000 | مدفوع |
| 2 | 1 سبتمبر | 10,000 | مدفوع |
| 3 | 1 أكتوبر | 10,000 | متأخر |
| 4 | 1 نوفمبر | 10,000 | مستحق |

**البيانات التي يحتويها كل قسط:**

| # | الحقل | # | الحقل |
|---|---|---|---|
| 1 | رقم القسط | 8 | المبلغ المدفوع |
| 2 | الاتفاقية التابع لها | 9 | المتبقي |
| 3 | تاريخ الاستحقاق | 10 | تاريخ السداد |
| 4 | قيمة القسط | 11 | حالة القسط |
| 5 | أصل الدين | 12 | غرامة التأخير |
| 6 | الفائدة (إن وجدت) | 13 | ملاحظات |
| 7 | الضريبة | | |

**العلاقة بين الاتفاقية والأقساط:**

```
InstallmentAgreement
        │
        │ 1
        │
        ├───────────────┐
        │               │
        ▼               ▼
 Installment      Installment
        ▼
 Installment
```

أي: اتفاقية واحدة تحتوي على عدد كبير من الأقساط.

```
installment_agreements
        1
        │
        │
        *
   installments
```

**مثال عملي:** تم بيع منتجات بقيمة 100,000 ريال، وأنشأ العميل اتفاقية:
- دفعة أولى: 20,000
- المبلغ الممول: 80,000
- عدد الأقساط: 8

النظام ينشئ تلقائياً:

```
Agreement #15
    financed_amount   = 80,000
    installments_count = 8

Installment #1 = 10,000
Installment #2 = 10,000
Installment #3 = 10,000
...
Installment #8 = 10,000
```

**هل الأقساط ترتبط بالفاتورة؟** يُفضَّل نعم.

```
فاتورة بيع
      │
      │1
      ▼
اتفاقية تقسيط
      │
      │1
      ▼
   الأقساط
```

وبذلك تستطيع معرفة:
- هذه الفاتورة نقدية أم بالتقسيط.
- كم تم سداده.
- كم تبقّى.
- الأقساط المتأخرة.

**ماذا يحدث عند دفع قسط؟**
1. تسجيل سند قبض.
2. تحديث حالة القسط (مدفوع أو مدفوع جزئياً).
3. تحديث رصيد الاتفاقية.
4. إنشاء قيد محاسبي.
5. تحديث رصيد العميل.
6. إذا تم سداد جميع الأقساط، تُغلق الاتفاقية تلقائياً.

## 9. أوامر التوريد (Purchase Orders — PO)

**الإصلاحات المطلوبة:**
- إصلاح الشريط الجانبي في أوامر التوريد.
- إصلاح اللودينج غير الدقيق في أوامر التوريد.
- **ربط كل ما سبق بفواتير أوامر التخزين وغيرها مع أوامر التوريد.**

**السؤال:** ما هي أوامر التوريد؟
**الإجابة:** هي مستند يصدره المشتري إلى المورد لطلب شراء منتجات أو مواد قبل استلامها، وهي مرحلة تسبق فاتورة التوريد واستلام المخزون.

**دورة الشراء الاحترافية:**

```
طلب شراء (Purchase Request)  [اختياري]
          │
          ▼
أمر توريد (Purchase Order)
          │
          ▼
استلام البضاعة (Goods Receipt)
          │
          ▼
فاتورة المورد (Purchase Invoice)
          │
          ▼
سداد المورد (Payment)
```

**الفرق بين أمر التوريد وفاتورة التوريد:**

| أمر التوريد | فاتورة التوريد |
|---|---|
| طلب شراء للمورد | مطالبة مالية من المورد |
| لا يؤثر محاسبياً | يسجّل قيداً محاسبياً |
| لا يزيد المخزون (إلا بعد الاستلام) | بعد اعتمادها يتم إثبات المديونية |
| يمكن تعديله أو إلغاؤه | وثيقة مالية رسمية |

**مثال:** أرسلت للمورد «أريد 100 كجم قات ممتاز + 50 كجم قات فاخر» — هذا **أمر توريد**. بعد يومين وصلت البضاعة وأرسل المورد فاتورة بقيمة 350,000 ريال — هذه **فاتورة توريد**.

**لماذا نحتاج أوامر التوريد؟** لأن الواقع ليس دائماً بهذه البساطة. قد يحدث:
- المورد يرسل نصف الكمية فقط.
- المورد يغيّر الأسعار.
- تصل البضاعة على عدة دفعات.
- يتم إلغاء بعض الأصناف.
- يحتاج المدير إلى اعتماد الطلب قبل الشراء.

كل هذه السيناريوهات تعالجها أوامر التوريد.

**البيانات الموجودة في أمر التوريد:**

| رأس الأمر | تفاصيل الأمر |
|---|---|
| رقم الأمر | المنتج |
| المورد | المتغيّر (Variant) |
| التاريخ | الكمية المطلوبة |
| العملة | السعر المتوقع |
| المستودع | الخصم |
| الحالة | الضريبة |
| ملاحظات | الإجمالي |

**حالات أمر التوريد (دورة الحياة):**

```
مسودة  Draft
      │
      ▼
معتمد  Approved
      │
      ▼
أرسل للمورد  Sent
      │
      ▼
استلام جزئي  Partial Received
      │
      ▼
مستلم بالكامل  Received
      │
      ▼
مفوتر  Invoiced

أو:  ملغي  Cancelled
```

**ماذا يحدث عند إنشاء أمر توريد؟** لا يحدث أي تأثير مالي — فقط يسجّل «نريد شراء هذه المنتجات». ولا:
- يزيد المخزون.
- ينشئ قيداً محاسبياً.
- ينشئ مديونية.

**ماذا يحدث عند استلام البضاعة؟** إذا كان النظام يعتمد الاستلام المنفصل، فينشئ **سند استلام مخزني (Goods Receipt)**. هنا فقط:
- يزيد المخزون.
- تُسجَّل حركات المخزون.
- يمكن تسجيل الكميات المستلمة جزئياً.

**ماذا يحدث عند تسجيل فاتورة المورد؟** هنا تبدأ المحاسبة. مثلاً بقيمة فاتورة 500,000 ريال:

```
مدين  : المخزون
مدين  : ضريبة المدخلات (إن وجدت)
دائن  : المورد
```

ثم عند السداد:

```
مدين  : المورد
دائن  : الصندوق أو البنك
```

## 13. عرض البيانات حسب الهرم الوظيفي

**المطلوب:** أن يرى كل مستخدم البيانات التي تخصّ موقعه في الهرم الوظيفي وما دونه فقط:

- **المندوب** يرى بياناته هو فقط.
- **المشرف** يرى بيانات الموظفين التابعين له.
- **المشرف الأعلى** يرى بيانات المشرفين والموظفين التابعين لهم.
- **المدير** يرى الكل.
- … وهكذا لأي عدد من المستويات.

**وأيضاً:** كل شيء في النظام يجب أن يرتبط بقسم أو فرع أو منطقة.

---

### 13.1 مستويات النطاق المقترحة (Scope Levels)

| المستوى | الاسم | ما يراه المستخدم | آلية التحديد |
|---|---|---|---|
| 1 | `own` — المندوب | سجلاته هو فقط | `created_by = auth()->id()` أو `employee_id = user.employee_id` |
| 2 | `team` — المشرف | سجلاته + كل التابعين له (مباشرة وغير مباشرة) | شجرة `employees.direct_manager_id` |
| 3 | `branch` — مدير الفرع | كل سجلات فرعه + الفروع/المناطق التابعة له | شجرة `branches.parent_id` |
| 4 | `region` — المشرف الأعلى / مدير المنطقة | كل الفروع والمجموعات تحت عقدة المنطقة | `branches` حيث `is_territory` / `node_type` |
| 5 | `all` — المدير العام | كل شيء بلا قيد | `is_main = 1` أو صلاحية `*_view_all` |

الهرم **مركّب من بُعدين معاً** — البُعد البشري (من يتبع من) والبُعد التنظيمي (أي فرع/منطقة):

```
المدير العام  (all)
      │
      ├── مدير المنطقة الشمالية  (region)
      │         │
      │         ├── مدير فرع الرياض  (branch)
      │         │         │
      │         │         ├── مشرف المبيعات  (team)
      │         │         │        ├── مندوب 1  (own)
      │         │         │        └── مندوب 2  (own)
      │         │         │
      │         │         └── مشرف التحصيل  (team)
      │         │                  └── محصّل 1  (own)
      │         │
      │         └── مدير فرع القصيم  (branch)
      │
      └── مدير المنطقة الجنوبية  (region)
```

**قاعدة الدمج:** المستخدم يرى السجل إذا تحقق **أيٌّ** من الشرطين:
1. مُنشئ السجل / الموظف المسؤول عنه ضمن `employee_ids` المسموحة له، **أو**
2. فرع السجل ضمن `branch_ids` المسموحة له.

### 13.2 ما هو موجود بالفعل في النظام ✅

الأساس البرمجي **جاهز بالكامل** ولا يحتاج بناءً من الصفر:

| المكوّن | الموقع | الحالة |

### 13.3 الفجوة الحرجة — لا يوجد `branch_id` في جداول المبيعات ⛔

هذه هي العقبة الأساسية أمام تنفيذ «كل شيء يرتبط بقسم أو فرع أو منطقة».

**نتيجة الفحص على قاعدة البيانات:**

| الجدول | `branch_id` |
|---|---|
| `invoices` | ❌ **غير موجود** |
| `quotes` | ❌ **غير موجود** |
| `payments_process` | ❌ **غير موجود** |
| `credit_notifications` | ❌ **غير موجود** |
| `installments` | ❌ **غير موجود** |
| `product_exchanges` | ❌ **غير موجود** |
| `periodic_invoices` | ❌ **غير موجود** |
| `supply_orders` | ❌ **غير موجود** |
| `journal_entries` | ✅ موجود |
| `clients` | ✅ موجود |
| `employees` / `users` | ✅ موجود |
| `purchase_invoices` | ✅ أُضيف لاحقاً في هجرة مستقلة |

**الآثار المترتبة على هذا النقص (كلها مرصودة فعلياً في الكود):**

1. **التقارير تفلتر الفرع بثلاث طرق بديلة هشّة** — لأنها لا تجد `branch_id` على المستند نفسه:
   ```php
   $q->whereHas('client', fn($s) => $s->whereIn('branch_id', $branchIds))   // فرع العميل
     ->orWhereIn('branch_id', $branchIds)                                    // فرع القيد
     ->orWhereHas('client', fn($s) => $s->whereExists(... neighborhoods ...)); // منطقة العميل
   ```
   ثلاثة مصادر مختلفة للحقيقة ⇒ نتائج مختلفة بين التقارير.

2. **اعتراف صريح في الكود** — [`Report/SalesProfitsController.php:269-270`](Http/Controllers/Report/SalesProfitsController.php#L269):
   ```php
   // ملاحظة: لا نفلتر على invoices.branch_id (العمود غير موجود) — فلترة الفرع
   // مطبقة بالفعل على القيود + clientsQuery أعلاه يجلب فقط عملاء الفروع المحددة
   ```
   أي أن كميات المبيعات والمرتجعات في تقرير الأرباح **غير مفلترة بالفرع إطلاقاً**.

3. **شاشات العمليات بلا فلترة فرع** (البند 6.4 في الجزء الثاني) — مدير الفرع يرى فواتير كل الفروع.

4. **إذا انتقل العميل من فرع لآخر، تنتقل معه فواتيره التاريخية** — لأن الفرع يُشتق من العميل لا من المستند. خطأ محاسبي جوهري: الفاتورة يجب أن تحتفظ بفرع إصدارها.

### 13.4 خطوات التنفيذ المقترحة

**الخطوة 1 — إضافة `branch_id` لكل جداول المبيعات (أساس كل ما بعده)**

```php
// هجرة جديدة
foreach ([
    'invoices', 'quotes', 'payments_process', 'credit_notifications',
    'installments', 'product_exchanges', 'periodic_invoices', 'supply_orders',
] as $tableName) {
    Schema::table($tableName, function (Blueprint $table) {
        $table->unsignedBigInteger('branch_id')->nullable()->after('id');
        $table->unsignedBigInteger('department_id')->nullable()->after('branch_id');
        $table->index(['branch_id', 'created_at']);
    });
}
```

**تعبئة البيانات التاريخية (Backfill):** استنتج الفرع بالأولوية التالية —
`journal_entries.branch_id` ← `users.branch_id` للمُنشئ ← `clients.branch_id` ← الفرع الرئيسي.

**التعبئة التلقائية للسجلات الجديدة** عبر Observer، حتى لا يعتمد الأمر على تذكّر المطوّر:

```php
class SetsBranchOnCreate
{
    public function creating(Model $model): void
    {
        $model->branch_id ??= auth()->user()?->branch_id;
        $model->department_id ??= auth()->user()?->employee?->department_id;
    }
}
```

**الخطوة 2 — خدمة نطاق موحّدة `DataScopeService`**

```php
namespace App\Services;

final class DataScope
{
    public function __construct(
        public readonly string $level,      // own | team | branch | region | all
        public readonly ?array $employeeIds, // null = بلا قيد
        public readonly ?array $branchIds,   // null = بلا قيد
    ) {}

    public function isUnrestricted(): bool
    {
        return $this->level === 'all';
    }
}

final class DataScopeService
{
    public function resolve(User $user): DataScope
    {
        // 1) المدير العام — بلا قيد
        if ($user->hasPermissionTo('data_scope_all')) {
            return new DataScope('all', null, null);
        }

        // 2) نطاق المنطقة / الفرع — شجرة الفروع
        if ($user->hasAnyPermission(['data_scope_region', 'data_scope_branch'])) {
            $branch = Branch::withoutGlobalScopes()->find($user->branch_id);
            $branchIds = $branch
                ? $branch->descendantBranchIds()->push($branch->id)->unique()->values()->all()
                : [$user->branch_id];

            $level = $user->hasPermissionTo('data_scope_region') ? 'region' : 'branch';

            return new DataScope($level, null, $branchIds);
        }

        // 3) نطاق الفريق — شجرة المدير المباشر
        if ($user->hasPermissionTo('data_scope_team') && $user->employee) {
            $ids = $user->employee->getDescendantIds();   // موجودة بالفعل
            $ids[] = $user->employee_id;

            return new DataScope('team', array_unique($ids), null);
        }

        // 4) الافتراضي — بياناته هو فقط
        return new DataScope('own', array_filter([$user->employee_id]), null);
    }
}
```

> **ملاحظة أداء:** `Employee::getDescendantIds()` ينفّذ استعلاماً لكل مستوى في الشجرة. مع شجرة عميقة يصبح مكلفاً في كل طلب — خزّنه في cache بمفتاح `user_scope:{id}` لمدة قصيرة، وأبطِله عند تعديل `direct_manager_id`. بديل أفضل على المدى الطويل: عمود `path` مادّي (Materialized Path) مثل `/1/7/23/` يجعل الاستعلام `LIKE '/1/7/%'` بمستوى واحد.

**الخطوة 3 — تطبيق موحّد عبر Trait**

```php
trait HasDataScope
{
    protected function applyScope(Builder $query, ?string $employeeColumn = 'employee_id'): Builder
    {
        $scope = app(DataScopeService::class)->resolve(auth()->user());

        if ($scope->isUnrestricted()) {
            return $query;
        }

        return $query->where(function ($q) use ($scope, $employeeColumn) {
            if ($scope->branchIds !== null) {
                $q->orWhereIn($query->getModel()->getTable() . '.branch_id', $scope->branchIds);
            }
            if ($scope->employeeIds !== null) {
                $q->orWhereIn($employeeColumn, $scope->employeeIds)
                  ->orWhereIn('created_by', $scope->employeeIds);
            }
        });
    }
}
```

الاستخدام في أي controller:

```php
$query = Invoice::query()->whereIn('type', ['normal', 'pos', 'online']);
$this->applyScope($query);          // سطر واحد يحلّ محل كل منطق الصلاحيات المتناثر
```

## 2. أخطاء حقيقية تؤثر على الأرقام (أولوية قصوى)

### 2.1 🔴 `$returnDetailIdsFlipped` غير معرّف — المرتجعات لا تُحسب

**الملف:** [`Report/CollectionsReportController.php:1250`](Http/Controllers/Report/CollectionsReportController.php#L1250)

```php
$isReturn = isset($returnDetailIdsFlipped[$detail->id]);   // ← المتغير غير موجود في الملف كله
```

المتغير `$returnDetailIdsFlipped` **لا يُسنَد له أي قيمة في أي مكان** داخل `CollectionsReportController.php`.
`isset()` على متغير غير معرّف تُرجع `false` دائماً بلا خطأ ظاهر ⇒

- `$isReturn` = `false` دائماً
- `$amount = (float) $detail->debit` بدل `-1 * $detail->credit` → **المرتجع يُحسب مبلغاً موجباً**
- `$totals['return_count']` و `$totals['return_amount']` = صفر دائماً
- `calculateStatistics()` يعطي إجمالي تحصيلات متضخّماً

للمقارنة، النسخة الصحيحة موجودة في [`PaymentsByCustomerController.php:504`](Http/Controllers/Report/PaymentsByCustomerController.php#L504):

```php
$returnDetailIdsFlipped = array_flip($returnDetailIds);   // ← السطر المفقود
```

**الإصلاح:** أضف السطر أعلاه قبل حلقة `foreach ($allDetails as $detail)` في السطر 1247.

### 2.8 🔴 `orWhereHas` بلا تجميع يُبطل كل الفلاتر السابقة

**الملف:** [`Installments/InstallmentsController.php:58-69`](Http/Controllers/Installments/InstallmentsController.php#L58)

الـ `orWhereHas` غير مُغلَّف داخل `where(function($q) {...})`، فيُنتج SQL بالشكل:

```php
$query->where(function ($q) {
```

### 5.2 🟠 `LIKE '%...%'` على عمود مفهرس يُعطّل الفهرس

**البادئة `%` تمنع MySQL من استخدام أي فهرس B-Tree** ⇒ full table scan.

| الملف | السطر | الكود |
|---|---|---|
| `ReturnInvoiceController.php` | 76 | `where('id', 'like', '%' . $request->invoice_number . '%')` |
| `QuoteController.php` | 149 | `where('id', 'LIKE', '%' . $request->id . '%')` |
| `SalesPaymentController.php` | 96 | `where('id', 'like', '%' . $request->payment_number . '%')` |
| `InstallmentsController.php` | 33 | `where('trade_name', 'like', '%' . $request->client . '%')` |
| `InvoicesController.php` | 370 | `whereHas('items', fn($q) => $q->where('item', 'like', '%...%'))` |
| `CreditNotificationController.php` | 118، 123-124، 169، 181 | 5 مواضع |
| `SupplyOrdersController.php` | 55، 59 | `order_number` و `name` |
| `SalesPaymentController.php` | 129، 133، 145 | `reference_number` × 2، `notes` |

**الإصلاحات المقترحة (حسب الحالة):**

1. **أعمدة رقمية** (`id`) → مطابقة تامّة أو `>=`:
   ```php
   ->when(is_numeric($term), fn($q) => $q->where('id', (int) $term))
   ```

2. **بحث بادئة** (أكواد، أرقام مرجعية) → `LIKE 'x%'` يستخدم الفهرس:
   ```php
   ->where('code', 'like', $term . '%')
   ```

3. **بحث نصي حقيقي** (أسماء، أوصاف، ملاحظات) → FULLTEXT:
   ```php
   // migration
   DB::statement('ALTER TABLE clients ADD FULLTEXT idx_clients_ft (trade_name, name)');
   DB::statement('ALTER TABLE invoice_items ADD FULLTEXT idx_items_ft (item, description)');

   // usage
   ->whereFullText(['trade_name', 'name'], $term)
   ```

## 6. تحسينات الفلترة

### 6.1 🟠 لا يوجد فرز (Sorting) قابل للتحكم

**كل** الجداول تستخدم `orderBy('created_at', 'desc')` ثابتاً. لا يمكن للمستخدم الفرز حسب المبلغ أو اسم العميل أو تاريخ الاستحقاق.

**المقترح — trait قابل لإعادة الاستخدام:**

```php
trait Sortable
{
    protected function applySorting($query, Request $request, array $allowed, string $default = 'created_at')
    {
        $column = in_array($request->input('sort'), $allowed, true)
            ? $request->input('sort')
            : $default;
        $dir = $request->input('dir') === 'asc' ? 'asc' : 'desc';

        return $query->orderBy($column, $dir);
    }
}

// الاستخدام

    'id', 'grand_total', 'invoice_date', 'due_value', 'payment_status', 'created_at'
```

### 6.2 🟠 الفلاتر تضيع عند التنقل بين الصفحات

**لا يوجد `->appends($request->query())` على أي paginator في الوحدة كلها.**

المستخدم يطبّق 6 فلاتر، ينتقل للصفحة 2 ⇒ تُفقد الفلاتر ويرى النتائج غير المفلترة.

### 6.3 🟠 `per_page` غير مُتحقق منه — ثغرة DoS

```php

$results = $query->paginate($perPage);
```

**المواضع:** `QuoteController:109`، `ReturnInvoiceController:105`، `CreditNotificationController:189`، `SalesPaymentController:176`، `ProductExchangeController:72`، `SupplyOrdersController:99`.

```php
$perPage = (int) $request->input('per_page', 10);
if (!in_array($perPage, [10, 25, 50, 100], true)) { $perPage = 10; }
```

### 6.4 🟠 لا فلترة بالفرع في شاشات العمليات

### 7.1 🔴 لا يوجد تصدير Excel/PDF في أي تقرير

**البحث في المجلد بأكمله:** لا توجد دالة `export()` واحدة في `Report/`. الاستيرادات الوحيدة لـ PhpSpreadsheet في `SalesReportsController:28-31` **غير مستخدَمة إطلاقاً**.

هذه ميزة **أساسية** في أي نظام ERP — المحاسبون يحتاجون البيانات في Excel.

**المقترح — trait موحّد:**

```php
trait ExportsReport
{
    public function export(Request $request, string $format = 'xlsx')
    {
        $payload = $this->buildReport($request);   // نفس دالة index

        return match ($format) {
            'xlsx' => Excel::download(
                new GenericReportExport($payload['reportData'], $payload['totals'], $this->columns()),
                $this->fileName($payload) . '.xlsx'
            ),
            'csv'  => $this->streamCsv($payload),
            'pdf'  => Pdf::loadView($this->viewName() . '_pdf', $payload)
                        ->setPaper('a4', 'landscape')
                        ->download($this->fileName($payload) . '.pdf'),
        };
    }
}
```

**متطلبات مهمة للتصدير العربي:**
- Excel: `maatwebsite/excel` مع `RTL` على ورقة العمل
- PDF: TCPDF مع `setRTL(true)` وخط `aealarabiya` (النمط المستخدَم بالفعل في [`SupplyOrdersController:375-387`](Http/Controllers/SupplyOrders/SupplyOrdersController.php#L375))
- استخدم `chunk()` أو `LazyCollection` للتصدير — لا تحمّل كل شيء في الذاكرة

### 7.2 🔴 تقرير أعمار الديون (Aging) مفقود

**المقترح:**

```php
$aging = DB::table('journal_entries as je')

    ->selectRaw("
        a.client_id,
        SUM(CASE WHEN DATEDIFF(?, je.date) <=  30                              THEN jed.debit - jed.credit ELSE 0 END) AS bucket_0_30,
        SUM(CASE WHEN DATEDIFF(?, je.date) BETWEEN  31 AND  60                 THEN jed.debit - jed.credit ELSE 0 END) AS bucket_31_60,
        SUM(CASE WHEN DATEDIFF(?, je.date) BETWEEN  61 AND  90                 THEN jed.debit - jed.credit ELSE 0 END) AS bucket_61_90,
        SUM(CASE WHEN DATEDIFF(?, je.date) BETWEEN  91 AND 120                 THEN jed.debit - jed.credit ELSE 0 END) AS bucket_91_120,
        SUM(CASE WHEN DATEDIFF(?, je.date) >  120                              THEN jed.debit - jed.credit ELSE 0 END) AS bucket_120_plus
    ", array_fill(0, 5, $asOfDate))

```

مع تلوين الشرائح وربطها بحالة العميل وحدّه الائتماني (`CreditLimit` موجود بالفعل في النظام).

### 7.4 🟠 لا مقارنة بفترة سابقة

لا يوجد أي دعم لـ period-over-period. المستخدم لا يرى «مقارنة بالشهر الماضي +12%».

**المقترح:**

```php
protected function withComparison(Request $request, callable $builder): array
{
    [$from, $to] = $this->parseDateRangeRequest($request);
    $current = $builder($from, $to);

    if (!$request->boolean('compare')) return ['current' => $current];

    $days = $from->diffInDays($to) + 1;
    $prevTo   = $from->copy()->subDay()->endOfDay();
    $prevFrom = $prevTo->copy()->subDays($days - 1)->startOfDay();

    $previous = $builder($prevFrom, $prevTo);

    return [
        'current'  => $current,
        'previous' => $previous,
        'delta'    => $this->calculateDelta($current, $previous),   // مبلغ + نسبة
    ];
}
```

```php
protected function cachedReport(Request $request, callable $builder)

            'employee_id','category_id','group_by','view_type','cascade_node',

}
```
